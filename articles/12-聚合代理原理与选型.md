# 把十几把免费钥匙串成一串：聚合代理原理与选型（freellmapi / One API / 9router / omniroute / bifrost 横评）

> 时效声明：本文数据核实于 **2026-09-06**。这几家迭代极快（omniroute 半年涨到 2 万+ star、freellmapi 目录每月变），文里那些"覆盖多少家、多少模型"的数字都是某一天的快照，你看到时以官网实时页面为准。

## 一、为什么我要写这篇

前面 01 到 09，我把国内外能白嫖的额度几乎盘了一遍。但你手上的 key 一旦攒到十几个，第一个真正的痛点就来了——**不是"哪里还能免"，而是"这么多家我到底怎么管"**。

我自己的真实体感是这样的：Claude Code 一个 `.env`、Cursor 一个设置、Codex 又一个设置；想换模型就得改代码里的 `base_url`；某个提供商限流了，工作流直接断在半路，得手动切。这事儿烦到一定程度，你就不再想"再多薅一家"，而是想"把这些破 key 统一管起来"。

这就是**聚合 / 中转层**存在的意义：在你和所有提供商之间架一层，对外只暴露**一个 OpenAI 格式的端点 + 一个 key**，背后帮你在 N 家之间路由、故障转移、压缩 token。你的 app、你的编码工具，从此只认这一个点。

但"聚合"这个词早被用滥了。我见过太多人把"能转格式的"和"能智能路由的"和"能压 token 的"混为一谈。所以动手比之前，先把三个概念掰扯清楚——这节是全文的地基，值得你多花两分钟。

---

## 二、先正本清源：聚合、路由、压缩，根本不是一回事

你听到的"网关""路由器""聚合代理"，落到代码上其实是三种不同的活儿：

- **聚合（Aggregation）**：把 N 家的 key 收拢成一个统一端点 + 一个统一 key。你的客户端只配一次，背后的 provider 随便换。典型代表：**One API、freellmapi**。
- **路由（Routing）**：请求进来了，按某种策略（优先级 / 成本 / 延迟 / 健康度）挑一个后端打出去。请求级决策。典型代表：**9router、omniroute、bifrost**。
- **压缩（Compression）**：在请求离开你机器之前，先把 token 砍掉——压输入（工具输出、长上下文）或压输出（让模型别啰嗦）。这是 **9router / omniroute** 的独门武器（RTK + Caveman）。

再加上一个**共同保底**——**故障转移（failover）**：主provider挂了或限流，自动切下一个，别把错误甩给你。

一句话总结：**有的工具只做聚合，有的只做路由，有的三者通吃，还有的顺手把压缩也做了。** 别被"AI 网关"四个字糊弄，往下看每家到底干了哪几件，你就知道该选谁。

## 三、五家逐个深挖

下面每家我都按同一套结构走：**一句话定位 → 怎么跑起来 → 最香的点 → 最坑的点 → 适合谁**。代码块里的命令都是能直接抄的。

### 3.1 freellmapi —— 专给"白嫖党"造的免费额度聚合器

**一句话**：把各家免费额度堆成一个"可用规模"的穷人版 OpenRouter。

它从立项第一天就说清楚了——**这是个把免费 API 当 OpenRouter 用的替代品**。你手上有 Google AI Studio、Groq、Mistral、Cerebras 这些免费 key，散着用很累，它把它们聚到一个 `/v1` 端点后面。

**怎么跑起来**（一行 Docker 安装，最省心）：

```bash
curl -fsSL https://freellmapi.co/install.sh | bash
```

脚本会建 `~/freellmapi`、生成加密密钥、拉镜像、起容器。然后开 `http://localhost:3001`，在 Keys 页填各家免费 key，拿一个 `freellmapi-` 开头的统一 key 给客户端用：

```python
from openai import OpenAI
client = OpenAI(
    base_url="http://localhost:3001/v1",
    api_key="freellmapi-your-unified-key",
)
resp = client.chat.completions.create(model="auto", messages=[{"role": "user", "content": "你好"}])
print(resp.choices[0].message.content)
```

`model="auto"` 让路由器自己挑；还能 `auto:fast` / `auto:smart` 偏速度或偏能力。它甚至实现了 Anthropic 的 `/v1/messages` 格式，所以 **Claude Code 也能直接接这个网关**走免费池子。

**最香的点**：
- 免费用，聚合 30+ 免费提供商、覆盖上百个免费模型；
- 6 种路由策略（priority / balanced / smartest / fastest / reliable / custom）；
- `fusion` 虚拟模型：把 prompt 扇出到多个免费模型并行，再用一个 judge 模型合成一个答案；
- key 用 AES-256-GCM 加密存本地，自适应路由用了 Thompson sampling bandit（这技术底子其实挺扎实）。

**最坑的点**（项目方自己写在 README 第一段）：
- **明确标注"仅限个人实验，非生产"**；
- 没有前沿模型，天花板就是开源权重（Qwen3 Coder、DeepSeek V3/R1、Kimi K2、GLM 那批）；
- 延迟波动大（Groq 毫秒、下一个可能 fallback 到慢端点），无 SLA；
- 单用户设计，没有多租户、没有按用户计费；
- 项目 2026 年 4 月才起，很新，生态还在早期。

**适合谁**：手上攒了一堆免费 key、想统一管、只做个人实验和学习的**原教旨白嫖党**。如果你是正经要上生产，它自己都会劝你"换付费 API 再发"。

### 3.2 One API —— 想把 key 当生意做的人用它

**一句话**：老牌 LLM API 管理与分发系统，国内开发者生态里最成熟的那一个。

它和前面几个"免费优先"的定位完全不同——它是**运营级**的。你不是拿来自己爽，是拿来**管一堆人、做配额计费、甚至二次分发卖 key** 的。

**怎么跑起来**（一行 Docker，端口 3000）：

```bash
docker run -d --name one-api -p 3000:3000 -e TZ=Asia/Shanghai -v /path/to/data:/data justsong/one-api
```

开 `http://localhost:3000` 就是一套完整后台。

**最香的点**：
- 聚合 100+ 提供商（OpenAI / Azure / Anthropic / Gemini / DeepSeek，外加文心、讯飞、混元、通义等国产全家桶）；
- 令牌管理极其完善：有效期、额度限制、IP 范围、模型访问权限；
- **兑换码**能批量生成导出（做分销/邀新的神器）；
- 多用户分组、渠道分组、不同倍率；
- 渠道降级（主渠道挂了自动切备用）、多机部署、流式、绘图接口、Cloudflare AI Gateway 集成。

**最坑的点**：
- 偏重、偏管理，个人玩家用它是**杀鸡用牛刀**；
- 要自己维护、自己盯渠道健康，运营责任在你；
- 功能多到第一次打开会懵，学习曲线不低。

**适合谁**：要管**多人 / 多团队 / 做二次分发**的中小站长、团队负责人。简单说——如果你的问题已经从"我想调模型"变成"我们团队几十号人怎么分额度、怎么计费"，One API 是正解。

### 3.3 9router —— 给"编码永不断线"的人造的路由

**一句话**：架在 AI 编程工具和各家模型之间的智能中间件，核心卖点是**订阅 → 廉价 → 免费三层降级，编码永不 429**。

它的诞生背景特别具体：一个人同时用 Claude Code（订阅）、Cursor、Codex，每家一个 key、一个配额、一种协议，限流了工作流就断。9router 把所有工具都指到 `http://localhost:20128/v1`，它来管。

**怎么跑起来**（npm 全局装，最省事）：

```bash
npm install -g 9router
9router   # 仪表盘自动开在 http://localhost:20128
```

然后把 Claude Code / Cursor / Cline 的 base_url 指过去就行。

**最香的点**（这三个是它的灵魂）：
- **RTK Token 压缩**：在请求到达 LLM 前，无损压缩工具输出（git diff、grep、ls、find、tree），典型能省 20–40% 输入 token——agentic loop 里这玩意儿太值钱了；
- **Caveman Mode**：注入"能少说就少说"的系统提示，压输出 token，最高省 65%；
- **三层自动降级**：订阅层（Claude Code/Codex）→ 廉价层（GLM $0.6/1M、MiniMax $0.2/1M）→ 免费层（Kiro AI、OpenCode Free、Vertex $300 额度），一层额度用完毫秒级切下一层；
- 双层翻译架构（OpenAI 当中间标准，14 种格式双向互转），连 Claude、Gemini、Cursor 的私有协议都能桥；甚至带 MITM 透明代理，能拦 CLI 硬编码的 API 端点。

**最坑的点**：
- 明显**偏编码场景**，纯聊天的需求用它有点绕；
- MITM 流量拦截有安全争议（要装本地 CA 证书、改 hosts），介意的人会不舒服；
- 项目新，踩坑得自己扛。

**适合谁**：重度 AI 编码（Claude Code / Cursor / Codex / Cline）、被限流打断心流、又想省 token 的人。它解决的就是"2 点还在写代码突然 429"这种痛。

### 3.4 omniroute —— 9router 的"堆料全家桶"兄弟

**一句话**：和 9router 撞了同一个端口（20128）、同一套路（RTK + Caveman + 三层降级），但把数字和功能的"堆料"做到了极致。

老实讲，omniroute 和 9router 是**直接竞品**。9router 有的它都有，它还在上面加料。所以这篇里这两家你二选一就行，别都装。

**怎么跑起来**（和 9router 几乎一模一样）：

```bash
npm install -g omniroute
omniroute   # 同样 http://localhost:20128
```

**最香的点**（堆料部分）：
- 目录号称 236–290 家提供商、90+ 免费，免费额度池去重后约 1.6B tokens/月；
- **17–18 种路由策略**（priority / cost-optimized / fusion / context-relay 等），比 9router 的"三层"细得多；
- **内置 MCP Server**（95–104 个工具）、A2A 协议、持久记忆（FTS5 + 向量）、guardrails、eval 框架——等于把 Agent 基础设施也塞进来了；
- 4 层降级（订阅 → API key → 便宜 → 免费），切换毫秒级。

**最坑的点**（这里要泼冷水）：
- 那些"290 家、1.6B token"是**项目方自报数字**，免费池去重计数虽然诚实，但各家上限浮动极大，别当真能稳定薅；
- 项目 2026 年 2 月才起，非常新，生产 benchmark 未必服众；
- 安全默认差：第一次启动 **管理员密码是字面量 `CHANGEME`**，不手动设 `INITIAL_PASSWORD` 就等于裸奔——这点必须改。

**适合谁**：想要"一个二进制搞定一切、不用自己拼插件"的懒人；编码 + Agent 通吃、愿意尝鲜的人。如果你纠结 9router 还是它——**要轻要专选 9router，要全要新选 omniroute**。

### 3.5 bifrost —— Go 仔的高性能网关新秀

**一句话**：Maxim AI 团队用 Go 从零写的企业级 AI 网关，Apache 2.0，主打一个"快"和"稳"。

前面四家要么是 TS/JS、要么是 Go 但偏运营。bifrost 的差异化很硬：**纯 Go、零 Python 依赖、性能取向**。它说自己 5K RPS 下每请求只加 11 微秒开销，号称比 LiteLLM 快 50 倍——这数字你当宣传看，但"Go 写的就是轻"这个体感是真实的。

**怎么跑起来**（npx 或 Docker，端口 8080，自带 Web UI）：

```bash
npx -y @maximhq/bifrost
# 或 Docker
docker run -p 8080:8080 maximhq/bifrost
```

开 `http://localhost:8080` 是仪表盘。调用同样是改 `base_url` 的 drop-in 玩法。

**最香的点**：
- 单一 OpenAI 兼容端点，统一 15–23+ 提供商、1000+ 模型；
- 自动故障转移带**熔断器**、**加权负载均衡**；
- **语义缓存**（相似请求复用，省 token 省延迟）；
- 同时是 **MCP client 和 MCP server**（这点比 9router/omniroute 的"仅 server"更灵活）；
- 虚拟 key + 预算、访问控制、Prometheus / OpenTelemetry 原生可观测——**运维该有的它都有**。

**最坑的点**：
- 比 LiteLLM 新太多，生产环境那些极端流量下的表现，得你自己压测验证，别盲信 benchmark；
- 集群、自适应负载均衡、自定义插件都在**企业版**，核心免费但上规模要谈钱；
- 生态比老牌网关薄。

**适合谁**：Go 技术栈、要**企业级可靠性和可观测**、不想被 Python 依赖和运维拖死的团队。个人玩家用它能跑，但有点杀鸡用牛刀。

## 五、特色 → 人群：你到底该装哪个

别贪多，这五家里**选 1–2 个够用**。按你的身份对号入座：

**① 纯白嫖个人玩家，手上十几个免费 key**
→ **freellmapi**。它存在的唯一理由就是把免费额度堆成规模，别家不干这活。

**② 重度 AI 编码，最恨限流打断心流，还想省 token**
→ **9router 或 omniroute，二选一**。要轻、要专、要稳，选 9router；要全功能、要 MCP、要尝鲜，选 omniroute。两者底层几乎一样，别都装。

**③ 团队 / 站长，要管多人、做配额计费、二次分发**
→ **One API**。它的令牌、兑换码、分组、倍率是正经营运级的，个人玩杀鸡用牛刀。

**④ 企业 / Go 技术栈，要性能、可靠性、可观测**
→ **bifrost**。Go 写的轻、熔断器+语义缓存+Prometheus 一套齐，前提是你能接受企业版才给集群。

**⑤ 懒得折腾、要"一个二进制全搞定"**
→ **omniroute**。它的哲学就是"batteries included"，路由、压缩、Agent 协议全塞进一个二进制，零插件。

决策树一句话版：**免费额度多 → freellmapi；编码老断 → 9router/omniroute；管人管钱 → One API；要性能稳 → bifrost。**

## 六、我的实际搭配建议

说点实在的，我自己现在怎么搭的：

- **个人零成本编码栈**：`freellmapi`（把免费额度堆起来当底座）+ `9router`（编码时智能路由 + RTK 压 token）。两者端口不冲突（3001 vs 20128），freellmapi 当 provider 池喂给 9router 也行，纯免费闭环。
- **团队场景**：`One API` 做分发和配额闸门，前面再怼一个 `bifrost` 当高性能网关做熔断和缓存。一个管人、一个管性能，分工清晰。
- **千万别五样全装**。聚合、路由、压缩这三种能力是有重叠的，装两套以上你自己的配置就会乱成一锅粥。

## 七、踩坑与收尾提醒

这几家虽然定位不同，但有几个**共性坑**，装之前先有心理准备：

1. **"免费聚合"≠"生产可用"**。freellmapi 自己写"仅限个人实验"；omniroute 的免费池数字会浮动；所有免费层都没有 SLA。真要上线，底下至少接一两个付费 provider 兜底。
2. **ToS 限制个人用途**。实测过，约一半免费模型的条款限制"个人/家庭用途"，商用的话老老实实走付费 API，别侥幸。
3. **安全默认别跳过**。omniroute 的 `CHANGEME` 密码、各家的 key 加密存储、别往网关传敏感数据（合同、客户名单、商业报价）——这些和前面几篇的纪律一致。
4. **数字都是快照**。今天写"290 家"，明天可能变。以官网实时为准，别拿本文当长期承诺。

折腾到这儿，免费 LLM 的世界我已经从"哪里能免"一路摸到了"怎么把免的管起来"。下一篇（系列第 13 篇）我会挑一个，手把手带你在免费云上把它**真正部署起来**——毕竟"能跑"和"跑得稳"之间，还差一次实战。

## 结尾：一句真心的

这几家我挨个装、挨个跑过，最大的感受是——**它们解决的不是"模型够不够强"，而是"我的工作流别断、我的 key 别乱、我的 token 别浪费"**。选谁不重要，重要的是你先想清楚自己属于上面哪类人：白嫖党、编码党、管人党、还是性能党。对号入座，装一个就够，剩下的交给它。

反正这五家我现在本地都留着镜像，但日常真正在跑的，也就那一两个。你要是也在纠结，照第五节的对号入座来，保准不踩我踩过的坑。
